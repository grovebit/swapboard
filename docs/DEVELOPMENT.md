# Developing ClipSync

This page is for people who want to build ClipSync themselves or change it. To *use* ClipSync, see the [README](../README.md).

## Architecture

```
ClipSync.app (menu bar) ─┐
Alfred workflow ─────────┼─► clipsync CLI ──unix socket──► clipsync agent (LaunchAgent) ◄══ WebSocket over Tailscale, AES-GCM ══► Android app
Terminal ────────────────┘
```

| Part | Where | What it is |
|---|---|---|
| Mac app + CLI | `mac/` | One Swift binary, `clipsync`, with no third-party dependencies. It's packaged as `ClipSync.app` and is also the command-line tool. `ClipSyncCore` holds the protocol, crypto, sessions, config and paths, and is unit-tested. |
| Alfred workflow | `workflow/` | Optional. `info.plist` and shell scripts that call `./clipsync`. Gives the `clip` keyword, hotkey, Universal Action and User Configuration. |
| Android app | `android/` | Kotlin + Compose. Contains: <ul><li>first-run setup screens</li><li>a foreground service (type `connectedDevice`)</li><li>the Quick Settings tile and share / text-selection targets</li><li>pairing (ML Kit code scanner or a pasted link)</li><li>the optional Shizuku clipboard watcher</li></ul> |
| Protocol | `protocol/` | [`PROTOCOL.md`](../protocol/PROTOCOL.md) is the wire spec. `vectors.json` holds test vectors that both test suites must pass. |

### Mac

**One binary, three modes** (`main.swift`):

- **No arguments, inside ClipSync.app (opened from Finder): the launcher** (`AppBundle.swift`). It:
  1. If the app is translocated or outside an Applications folder, offers to move it there. The original location comes from `SecTranslocateCreateOriginalPathForURL`, looked up with `dlsym`. Then it removes quarantine and relaunches.
  2. Restarts the agent unless it already runs this exact build from this exact path. The comparison uses `ExecutableStamp` and `launchctl print`.
  3. Sends the control request `show` and exits.
- **`agent`:** the long-running process, started by launchd. Inside the app bundle it also shows the menu-bar item (`AgentUI.swift`) and the setup window (`SetupWindow.swift`, SwiftUI using only macOS 12 APIs).
- **Anything else:** the CLI, which talks to the agent over the control socket.

**Agent lifecycle (`LaunchAgentManager.swift`)**
- `start` writes `~/Library/LaunchAgents/com.clipsync.agent.plist` and bootstraps it. The plist runs:
  - the installed `ClipSync.app` executable, or
  - for Alfred-only installs, a private copy in `<data>/bin/`.
- **KeepAlive.** `KeepAlive` is `{SuccessfulExit: false}`:
  - crashes restart the agent,
  - **Quit** (exit code 0) doesn't.
- **Open at Login off** removes the plist after bootstrapping. The job stays loaded for the session, but isn't loaded at the next login.
- **Uninstall ClipSync…** removes the plist and the data folder, moves the app to the Trash, and exits with code 0.

**Data folder:** `~/Library/Application Support/ClipSync/`. `CLIPSYNC_DATA_DIR` overrides it, for tests. It contains:
- `config.json` (mode 0600): pairings and settings
- `agent.log`
- `agent.sock`: the control channel between the CLI and the agent
- `pair-qr.png`, only for the Quick Look fallback

Versions before 1.4 used Alfred's workflow data folder. `Paths.resolveDataDir` keeps using it until `LaunchAgentManager.start()` has stopped the old agent and moved the files (`Paths.migrate`, unit-tested).

**Settings**
- The menu bar sets `notifyOnReceive`, `openAtLogin` and `paused`.
- Alfred passes User Configuration values only to the scripts it runs, so every CLI call copies changed values into `config.json` and sends `reload`.
- Without Alfred, the other keys in `config.json` → `settings` are `port`, `maxClipKB` and `ignoredApps`. Restart the agent after editing them by hand.

**Clipboard.** The agent polls `NSPasteboard.changeCount`. It skips:
- items with the [nspasteboard.org](http://nspasteboard.org) `Concealed`, `Transient` or `AutoGenerated` markers,
- copies made while an ignored app is frontmost,
- its own writes, which carry `com.clipsync.remote`.

Received sensitive clips are written with `org.nspasteboard.ConcealedType`.

**Notifications.** Inside the app bundle they go through `UNUserNotificationCenter`. Otherwise they go through the workflow's External Trigger, or `display notification` without Alfred.

### Android

- minSdk 29 (Android 10), target and compile SDK 37. Newer APIs are behind version checks, and lint must report no `NewApi` errors.
- **First-run setup.** `SetupScreen.kt` shows the step that `currentSetupStep()` (`SetupFlow.kt`, unit-tested) picks from what's already done. Phones that were paired before this screen existed skip it (`SetupPrefs.decideOnce`).
- **Tailscale detection.** `TailscaleApp` looks for a VPN network carrying a 100.64.0.0/10 address, or routing 100.100.100.100. That needs the `<queries>` entry for `com.tailscale.ipn`.
- **Key storage.** The pairing key is wrapped with an Android Keystore AES-GCM key. App backups are disabled.
- **Automatic phone → Mac.** Android 10+ only lets the foreground app read the clipboard, but the shell user (uid 2000) holds `READ_CLIPBOARD_IN_BACKGROUND`. `shizuku/ClipWatcherService` runs as a Shizuku *user service* under that uid:
  - it registers a clipboard listener on the hidden `IClipboard` service, falling back to polling;
  - it hands new text to the app over AIDL;
  - the app filters what it receives with `clip/AutoSendFilter`.

### Tailscale only (keep it that way)

ClipSync deliberately never talks over the LAN.
- **Mac:** the listener binds to the Mac's Tailscale IPv4 (100.64.0.0/10) through `requiredLocalEndpoint`.
  - It rejects peers outside that range.
  - It rejects connections that arrive on a Wi-Fi, Ethernet or cellular interface.
  - When Tailscale comes up or its address changes, it re-binds.
- **Android:**
  - `TailnetPolicy` drops every pairing host that isn't a Tailscale address.
  - `TailscaleNetwork` binds the socket to the VPN network whose routes cover the host.
  - Without that VPN, the app doesn't connect at all.
  - The app doesn't hold `ACCESS_LOCAL_NETWORK`.

Please don't add a LAN, mDNS or Wi-Fi fallback.

## Requirements

- macOS with Xcode or the Xcode command-line tools (Swift 6)
- Android Studio, with Android SDK platform `android-37.0`
  - The project uses AGP 9.2.1 and the Gradle 9.5.0 wrapper.
  - `make` runs Gradle with Android Studio's bundled JDK when it finds one.
- Node.js 18 or newer, only to regenerate the protocol test vectors

## Make targets

| Command | What it does |
|---|---|
| `make test` | Swift and Kotlin unit tests. Both run `protocol/vectors.json`. |
| `make test-mac` / `make test-android` | One side only. |
| `make app` | `dist/ClipSync.app` and `dist/ClipSync-mac.zip`: a universal (arm64 + x86_64) build for macOS 12+, signed (see below). |
| `make install-app` | Copies the app to `/Applications` and opens it; it takes over from a running agent. |
| `make mac` | Builds the bare `clipsync` binary into `workflow/clipsync`, for the Alfred workflow. |
| `make dev-install` / `make dev-uninstall` | Symlinks `workflow/` into Alfred, so edits take effect immediately / removes the link. |
| `make package` | `dist/ClipSync.alfredworkflow`. |
| `make android` / `make install-android` | Debug APK / install it on the phone connected over adb. |
| `make apk` | Signed release APK at `dist/ClipSync.apk` (see "Releasing"). |
| `make vectors` | Regenerates `protocol/vectors.json` with Node's crypto, which serves as an independent reference implementation. |
| `make clean` | Removes build outputs. |

The version of both apps comes from the `VERSION` file. `PROJECT_URL` is derived from the git remote, or from `GITHUB_REPOSITORY` in CI, and is used for the app's "get the Android app" QR code and its Help links.

### Code signing on the Mac

By default, builds are signed ad hoc (`SIGN_ID=-`). An ad-hoc signature changes on every build, so macOS may ask its permission questions again after a rebuild. To avoid that, sign with a stable identity:

```sh
make app SIGN_ID="Apple Development: Your Name (TEAMID)"
```

## Releasing

1. Bump `VERSION` and commit.
2. Tag and push:

   ```sh
   git tag v1.4.0 && git push origin v1.4.0
   ```

   The tag must match `VERSION`.
3. `.github/workflows/release.yml` tests everything, builds `ClipSync-mac.zip`, `ClipSync.apk` and `ClipSync.alfredworkflow`, and publishes the release.

To try a build without publishing, run the **Release** workflow by hand. It makes a draft pre-release, `vX.Y.Z-test.N`.

**Secrets:**

| Secret | Required | What it is |
|---|---|---|
| `CLIPSYNC_KEYSTORE_BASE64` | yes | The Android release keystore, base64-encoded |
| `CLIPSYNC_KEYSTORE_PASSWORD` | yes | Its password |
| `CLIPSYNC_KEY_ALIAS` | yes | Its key alias |
| `MACOS_CERTIFICATE_P12`, `MACOS_CERTIFICATE_PASSWORD` | no | A Developer ID Application certificate (base64 .p12) and its password |
| `MACOS_SIGN_ID` | no | For example `Developer ID Application: Your Name (TEAMID)` |
| `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD` | no | For notarization; the password is an app-specific password |

With the Apple secrets, the Mac app and the workflow binary are signed with Developer ID and the hardened runtime, then notarized, and the app is stapled. macOS then opens ClipSync without any warning. Without them, the Mac downloads are signed ad hoc.

**The Android signing key.**
- Every update must be signed with the same key, or it won't install over an existing installation. **Keep a backup of the keystore and its password.**
- To build a signed APK locally, set these variables, then run `make apk`:
  - `CLIPSYNC_KEYSTORE`
  - `CLIPSYNC_KEYSTORE_PASSWORD`
  - `CLIPSYNC_KEY_ALIAS` (optional; defaults to `clipsync`)

## Testing the Mac side without a phone

`clipsync debug-client` acts as a fake phone. To keep the test away from your real setup, use a separate data directory and port:

```sh
export CLIPSYNC_DATA_DIR=/tmp/clipsync-test
mkdir -p $CLIPSYNC_DATA_DIR && echo '{"settings":{"port":48699}}' > $CLIPSYNC_DATA_DIR/config.json
clipsync agent &                         # agent in the foreground of this shell
clipsync pair --no-show                  # creates a pairing without showing the QR code
clipsync debug-client --exit-after 10    # prints the clips the Mac sends
clipsync debug-client --send "hello"     # sends a clip to the Mac
clipsync debug-client --wrong-key        # expect: closed code=4001
```

The agent still listens only on the Mac's Tailscale address, so Tailscale must be connected.

**Setup window pages.** Debug builds have `clipsync debug-snapshots DIR`. It asks a running agent (inside an app bundle) to render every setup page to a PNG, without opening a window.

## Ground rules

- Never log clipboard text. Log sizes and device names only.
- Keep automatic phone → Mac off by default.
- Keep user-facing text plain and keep labels identical across the apps and the README. The README is written for non-technical readers.
- Any protocol change must update `PROTOCOL.md`, the vector generator and both test suites, together.
